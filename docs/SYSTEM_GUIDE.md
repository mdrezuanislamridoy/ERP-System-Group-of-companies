# Okobiz ERP — System Guide

*What each part of this repo is, what lives inside it, and why it's built the way it is.*

This is the orientation doc: read this first, before `BACKEND_CREATION_AND_INTEGRATION_GUIDE.md` (which is the section-by-section build spec) or `GITHUB_ISSUES_AND_WORKFLOWS_BY_SECTION.md` (the backlog).

---

## 1. The four top-level pieces, and how they relate

```
ERP-System-Okobiz/
├── architecture/   — a rendered spec/ADR document (what to build, and why)
├── backend/        — the real API (NestJS + Prisma + PostgreSQL)
├── design/         — the UI (React + Vite), mock-data-first prototype
└── docs/           — build guides and backlog (markdown, this file included)
```

The mental model that makes this repo make sense:

1. **`architecture/`** is the *decision record*. Someone wrote out, section by section, what this ERP should be — org model, IAM, finance, HR, workflow, data model, API shape, rollout plan — with explicit trade-offs for each decision. It renders as a little in-browser doc viewer. Nothing here executes; it's the brief.
2. **`design/`** is the *prototype*. It was generated by Magic Patterns as a fully clickable, fully fake (mock-data) ERP UI — every screen described in the architecture doc, rendered with realistic-looking data generated in TypeScript modules, with no server required. Its job is to let you see and interact with the whole product before the backend catches up.
3. **`backend/`** is the *real system* — being built to match the architecture doc, one module at a time. It is **behind** the prototype: some modules (auth, IAM, organizations, HR) are fully real; others (procurement, inventory, workflows) only have a couple of read endpoints; finance has no frontend wiring at all yet despite being fairly built out.
4. **`docs/`** tracks the gap between 2 and 3 — which section needs backend endpoints, what shape they should be, and what frontend file to wire them into once they exist.

**The single most important thing to understand about this repo**: `design/` almost never talks to `backend/`. Only `Companies.tsx`, `Employees.tsx`/`EmployeeDetail.tsx` (partially), and `IAM.tsx` call the real API. Everything else — Finance, Procurement, Inventory, Workflows, Approvals, Reports, Audit Logs, the HR/Payroll feature — runs entirely against in-memory TypeScript data modules under `design/src/data/`. This is intentional (it's how the prototype works standalone), but it's also the source of the two real bugs found in this repo so far — see [§6 Known fragility](#6-known-fragility--lessons-learned).

## 2. `architecture/` — the spec

A separate Vite/React app, same Magic Patterns template as `design/`. Run it (`npm install && npm run dev`) and you get a static documentation viewer: a sidebar of sections, a main pane that renders one section at a time, prev/next paging. No routing, no API calls — it's a document, not a tool.

The content lives as **typed TypeScript data**, not markdown, under `architecture/src/data/sections/`:

| File | Sections |
|---|---|
| `foundation.ts` | executive summary, business requirements, principles |
| `access.ts` | org hierarchy, IAM, authz (ABAC), role hierarchy |
| `domains.ts` | module system, finance, HR, procurement, inventory, sales |
| `platform.ts` | workflow engine, audit, notifications, reporting |
| `data.ts` | database design, ERD, schema, API conventions, events, security (largest file) |
| `operations.ts` | frontend architecture, infrastructure, scalability, observability, backup/DR |
| `reference.ts` | worked scenarios, permission matrix, workflow examples |
| `delivery.ts` | roadmap, risks, final notes |

Each section is built from typed content blocks (`architecture/src/types/doc.ts`): `p`/`h`/`ul` for prose, `table`/`erd` for data shapes, `tree`/`flow`/`cards` for diagrams, and — the most useful one — `decision`, an ADR block with `decision`, `why`, `tradeoffs`, `alternatives`, and `changeWhen` fields. E.g. the platform's foundational decision is recorded verbatim as:

> *"Modular monolith (NestJS + TypeScript + Prisma) on a single PostgreSQL cluster with a shared schema, organization-scoped rows, and an analytics replica for reporting."*

**Why it exists**: so that "why did we choose X" has one answer, written down once, instead of being re-litigated per PR. When you're unsure *why* the backend does something a particular way (e.g. why ABAC scope is resolved the way it is, why audit logs are hash-chained), check `access.ts` / `platform.ts` / `data.ts` first — the reasoning is usually already written there.

## 3. `backend/` — the real API

**Stack**: NestJS 10 + TypeScript, Prisma ORM, PostgreSQL (`docker-compose.yml` spins up Postgres + Redis + pgAdmin), JWT auth. Entry point `backend/src/main.ts`, root module `backend/src/app.module.ts`. All routes are under `/api/v1/...`.

### 3.1 How a request flows

1. `RequestContextMiddleware` runs first on every request — stamps a correlation ID, captures IP/user-agent, seeds `req.context` (see `common/interfaces/request-context.interface.ts`).
2. `JwtAuthGuard` (on guarded routes) verifies the bearer token, loads the user + their active `UserRoleAssignment` + role + permissions, resolves an `UserScope` (allowed companies, descendant org IDs via the `OrganizationClosure` closure table, financial approval limit), and fills in `req.context.user` / `req.context.scope`.
3. `PermissionsGuard` + `@RequirePermissions('x.y.z')` checks the resolved permission list against what the route declares.
4. Services that touch scoped data extend `ScopedRepository` (`common/repositories/scoped.repository.ts`), whose `buildScopeFilter()` turns `req.context.scope` into a Prisma `where` clause — this is the actual ABAC enforcement point. It **fails closed**: no scope on the context → `UnscopedQueryError` (403), not an open query.
5. Mutating actions call `AuditService.log(...)`, which SHA-256 hash-chains each row to the previous one (`prevHash` → `rowHash`), so tampering with history is detectable (`GET /api/v1/audit/verify` walks the chain).

### 3.2 Modules — what's real vs. stub

| Module | Base path | Maturity | What it actually does |
|---|---|---|---|
| `auth` | `/api/v1/auth` | **Full** | Login (bcrypt + brute-force lockout: 5 fails → 15 min lock), refresh-token rotation **with reuse-detection** (a replayed refresh token revokes every session for that user and logs a `SECURITY_ALERT`), `switch-context` (pivot active org/company via direct or SUBTREE-closure-table assignment), session list/revoke, `/me`. Every auth event is audit-logged. |
| `iam` | `/api/v1/iam` | **Full** | List directory users (field-level salary/bank masking unless caller holds `sensitive.salary.read`), provision new employee+user+role-assignment transactionally (with privilege-escalation checks — can't grant `group-super-admin` without holding it yourself), list roles/permissions. |
| `organizations` | `/api/v1/organizations` | **Full** | Hierarchy tree, company (legal entity) CRUD, per-company module activation (`PUT /companies/:id/modules` — this is the backend half of the "enabled modules" feature the frontend's `EntityScopeContext` also implements client-side), org-unit (branch/dept/cost-center/etc) CRUD. |
| `finance` | `/api/v1/finance` | **Full**, not wired to frontend | Chart of accounts, double-entry journal posting (validates debits == credits, updates running account balances in a transaction), trial balance. No `financeApi` exists in `design/src/api/client.ts` yet — `FinanceOverview.tsx`/`ChartOfAccounts.tsx` still use mock data. |
| `hr` | `/api/v1/hr` | **Full**, not wired to frontend | Attendance clock-in/out + register, salary structures, payroll run generation + finalization (posts a real GL journal entry: Dr Salaries & Wages / Cr Salaries Payable). Added this session — see §3.4. Frontend `design/src/pages/HR.tsx` runs entirely against `design/src/data/payroll.ts` + `data/attendance.ts` instead, by design (see §4.4). |
| `procurement` | `/api/v1/procurement` | **Stub** | 4 endpoints: list/create purchase requests, list purchase orders, list suppliers. No RFQ, quote comparison, PO approve/issue/cancel/print, GRN, or supplier CRUD — all of which already exist as full mock flows in `design/src/pages/Procurement.tsx`. |
| `inventory` | `/api/v1/inventory` | **Stub** | 2 read-only endpoints: stock list, per-item ledger. No goods receipt, adjustment, transfer, batch/recall, or RTV — all present in `design/src/pages/Inventory.tsx` mocks. |
| `workflows` | `/api/v1/approvals` | **Stub** | 2 endpoints: unified approval inbox, approve/reject a task. No workflow-definition CRUD, delegation rules, or SLA handling (present in `Approvals.tsx`/`WorkflowBuilder.tsx` mocks). Also notably **missing `PermissionsGuard`** — only JWT-authenticated, not permission-checked, unlike every other module. |
| `audit` | `/api/v1/audit` | **Full** | Scoped log retrieval, hash-chain verification. |
| `platform` | — (no controller) | **Full** | `NumberSequenceService` — gapless, concurrency-safe document numbering (`PR-2026-000001`, `JOURNAL-FOODS-2026-000004`, etc.), one counter per `(companyId, documentType, fiscalYear)`. |

### 3.3 Data model (`backend/prisma/schema.prisma`)

Grouped roughly as the file itself groups them:

1. **Org hierarchy & multi-tenancy** — `Organization` (self-referencing tree: GROUP → LEGAL_ENTITY → BUSINESS_UNIT → BRANCH_PLANT → DEPARTMENT/COST_CENTER/...), `OrganizationClosure` (precomputed ancestor/descendant pairs — what makes SUBTREE-scope queries and `switch-context` fast instead of recursive), `CompanyModule` (per-company feature flags).
2. **IAM** — `Person` (the human; holds salary/bank/NID — the sensitive fields) vs `User` (the login credential, 1:1 with `Person`) vs `Role`/`Permission`/`RolePermission` (RBAC) vs `UserRoleAssignment` (the actual grant: user × role × organization × scope mode — this is what ABAC resolves from) vs `Session` (refresh-token tracking).
3. **Finance** — `Account` (chart of accounts, company-scoped or global), `JournalEntry`/`JournalLine` (double-entry, immutable once posted).
4. **Procurement** — `Party`, `PurchaseRequest`, `PurchaseOrder`/`PurchaseOrderLine`.
5. **Inventory** — `StockItem`, `StockLedger` (append-only movement log).
6. **Workflow engine** — `WorkflowDefinition`/`WorkflowInstance`/`WorkflowTask` (generic polymorphic approval chain, not tied to one document type).
7. **HR / payroll** *(added this session)* — `AttendanceRecord` (one row per person per day, unique constraint enforces that), `SalaryStructure` (Basic/HRA/Medical/Conveyance/Other breakdown per person), `PayrollRun` (one per company+month+year, unique constraint prevents double-running), `Payslip` (one per run per person, computed: PF 5% of basic, simplified tax, loss-of-pay deduction prorated from that month's attendance).
8. **Platform core** — `AuditLog` (hash-chained), `NumberSequence`, `Setting`, `OutboxEvent` (outbox pattern scaffold for eventual async integration events — not yet consumed anywhere).

### 3.4 The ABAC / scope model, concretely

`UserScope` (`common/interfaces/request-context.interface.ts`) carries: `scopeMode` (`SELF | NODE | SUBTREE | SUBTREE_EXCEPT | CROSS`), `activeCompanyId`, `allowedCompanyIds` (`['*']` for group-level roles), `descendantOrgIds` (pre-expanded from the closure table), and `financialApprovalLimit`. `ScopedRepository.buildScopeFilter()` turns that into a Prisma filter per scope mode — e.g. `SUBTREE` filters by `{ orgField: { in: descendantOrgIds } }`, `CROSS` by `{ companyField: { in: allowedCompanyIds } }`. `AbacPolicyService` provides the imperative assertions services call directly (`assertCompanyScope`, `assertOrgNodeScope`, `assertFinancialApprovalLimit`, `assertSegregationOfDuties` — the last one blocks a user from approving their own request).

## 4. `design/` — the frontend prototype

**Stack**: React 18 + Vite + TypeScript + Tailwind, React Router v6, no state library (Context API only). Dev server defaults to `:5173`, proxies `/api/*` to `localhost:4000` (`vite.config.ts`) — i.e. the real backend, when it's running.

### 4.1 Two parallel login paths — this matters

`AuthContext.login()` tries **local mock-directory auth first** (`data/directory.ts` — a hardcoded list of demo users/passwords, instant, no network), and only falls back to a real `authApi.login()` call if the ID isn't in that local directory. This means:

- The default/demo experience never touches the backend at all.
- But several pages (`Companies.tsx`, `Employees.tsx`, `IAM.tsx`) call the real API regardless of which login path was used.
- If the real backend happens to be reachable but the session is a local-mock one (no real JWT was ever issued), those calls get a perfectly correct `401` from the backend — which used to force a **global logout**, because `api/client.ts` treated *any* 401 as "your session was revoked." **Fixed this session** (see §6) — it now only force-logs-out when a token was actually sent and rejected.

### 4.2 Two parallel permission systems — also matters

- **Frontend**: `data/roles.ts` — a hardcoded `roleTemplates` map, permission strings like `'payroll.read'`, `'employee.read'`, `'sensitive.salary.read'`. `useApp().can(permission)` checks this. Entirely client-side, entirely fake — there is no server round-trip.
- **Backend**: real `Permission`/`RolePermission` rows seeded in `backend/prisma/seed.ts`, permission strings like `'hr.payroll.read'`, `'finance.gl.post'`. Checked by `PermissionsGuard` + `@RequirePermissions()`.

**These two permission vocabularies don't fully overlap by name**, and that's fine — they're answering different questions for different consumers (frontend demo gating vs. real API authorization). Don't assume adding a permission string in one place does anything in the other.

### 4.4 The `data/` layer — a fake backend written in TypeScript

Everything under `design/src/data/*.ts` is a self-contained "mock service": typed interfaces, a deterministic generator or seed array, and exported functions that read/mutate module-level state (`let` arrays, `Record<id, T>` maps) with a pub/sub `subscribe...()` pattern for reactivity — e.g. `data/people.ts`'s `leaveRequests` + `createLeaveRequest()`/`decideLeaveRequest()`, or `data/payroll.ts`'s `payrollRuns`/`runPayroll()`/`finalizePayrollRun()`. This is why the prototype is fully interactive (you can actually run payroll, approve leave, etc.) without any server — and why it resets on every page reload, since it's just JS module state, not persisted anywhere.

The HR/Payroll feature added this session deliberately followed this exact convention (rather than wiring to the new `hr` backend module) to stay consistent with how every other unwired page in this prototype already works — see `docs/BACKEND_CREATION_AND_INTEGRATION_GUIDE.md` §9 for the documented endpoint contracts to wire up later.

### 4.5 Contexts

| Context | Owns |
|---|---|
| `AuthContext` | Session (who's logged in), the two-path login described in §4.1, assignment switching |
| `AppContext` | Derives a `RoleProfile` from the active assignment + `roleTemplates`; exposes `can()`, active company/branch, palette/notification UI state |
| `EntityScopeContext` | The ABAC "lens": `allowedCompanyIds` → `activeCompanyId`/`activeBranchId` (narrower-than-allowed drill-down, re-validated against the allowed set on every change), `companyModules` + `isModuleEnabled()` (client-side mirror of the backend's per-company module toggle), `canApproveAmount`, and dataset-filtering helpers (`filterEmployees`, `filterInvoices`, etc.) used throughout the mock pages |
| `ThemeContext` | Light/dark/system theme, persisted to `localStorage`, OS-preference listener — unrelated to auth/scope |

## 6. Known fragility & lessons learned

Two real bugs were found and fixed by actually driving the app (headless browser) rather than static review — both are good examples of *why* things are built the way they are:

1. **"Clicking a page logs me out."** Root cause: §4.1's two-login-paths gap — a local-mock session making a call to a reachable real backend gets a legitimate 401, which the client used to treat as "session revoked" and force-logout globally. **Fix**: `api/client.ts` now only force-logs-out when a *token was actually sent and rejected*, not on any 401. **Lesson**: if you see an unexpected logout, check whether the real backend is running (`netstat`/`curl localhost:4000`) before assuming it's a frontend bug — it very likely is this exact interaction.
2. **"A page crashes the app on click."** Root cause: `CreatePurchaseRequestModal.tsx` had `if (!isOpen) return null` placed *before* a `useMemo()` call — a React Rules-of-Hooks violation that only manifests the moment the modal transitions from closed→open (mismatched hook count between renders → full crash, no error boundary to catch it). Every other modal in the codebase (13 checked) correctly puts the early return *after* all hooks. **Lesson**: when writing a new modal component, hooks first, `if (!isOpen) return null` last — grep `if (!isOpen) return null` across `components/**/*.tsx` to find the established pattern before writing a new one.

Both are instructive because **static checks (`tsc`, `vite build`) did not catch either one** — both are runtime-only failures (an auth race and a hooks-order crash). When something is "not working" in this app and type-checking is clean, the next step is to actually run it and click, not re-read the diff.
